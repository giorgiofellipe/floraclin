# NFS-e Emission After Payment Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A clinic with an A1 e-CNPJ certificate issues an NFS-e Nacional for a patient payment from FloraClin, by prompt ("ask") or automatically ("always"), with PDF/XML download, cancellation and optional email to the patient.

**Architecture:** `@bullcode/fiscal` builds, signs and sends the DPS. FloraClin stores an encrypted certificate and fiscal settings per tenant and keeps an `nfse_documents` outbox (one active row per payment record). Rows are created inside the payment transaction (`always`) or by an explicit emit request (`ask`/manual), processed after commit, and swept by a deadline-bounded cron that also retries cancellations and backfills missed `always` rows. Copies Revezza `staging` (commit e8e96e30) where it fits.

**Tech Stack:** Next.js 16 App Router (`web/`), Drizzle + Postgres (`floraclin` schema, hand-written SQL migrations), TanStack Query, Resend, Vitest, `@bullcode/fiscal` v0.1.1.

**Spec:** `docs/superpowers/specs/2026-11-02-nfse-design.md`

## Global Constraints

- Library: `"@bullcode/fiscal": "git+https://github.com/bullcodeapps/fiscal.git#v0.1.1"` in `web/package.json` dependencies; `node-forge` and `@types/node-forge` in devDependencies (test certificate factory).
- `NFSE_NACIONAL_ENVIRONMENT` = `production` | `restricted`. When `NODE_ENV === 'production'` and unset: throw. Elsewhere default `restricted`. The environment is stored on each document at creation; emit, reconcile and cancel use the document's value, never the current env.
- Install needs `FISCAL_REPO_TOKEN` (git `insteadOf`). Never print it.
- DPS series `"00800"`, `verAplic` `"floraclin"`, `dhEmi` = now minus 60 s.
- Secrets via `encryptSecret` / `decryptSecret` (`web/src/lib/crypto.ts`). pfx/password only read by `getNfseSettingsWithSecrets`; never returned by an API; scrubbed from Sentry.
- Upload limits: pfx base64 at most 64 KB, password at most 200 chars. Reject expired, not-yet-valid, and (on replacement) a different CNPJ than the stored one (409 `CERTIFICATE_CNPJ_CHANGED`, "Remova o certificado atual para usar outro CNPJ.").
- Dates: BR calendar days via `toBrYmd`, `brToday`. Display a `YYYY-MM-DD` with `formatBrDate(parseBrDate(ymd))` (never `formatBrDate(ymd)`, it flips the day). Instants with `formatBrDate(date)`.
- Payment recording never fails, slows or rolls back because of NFS-e:
  - NFS-e settings are read **before** the payment transaction with the global pool, inside try/catch (failure → treat as not configured). No global-pool read inside the payment transaction (`financial.ts:150-160` deadlock note).
  - Inside the transaction, every NFS-e statement runs in one `SAVEPOINT nfse_outbox` with `ROLLBACK TO SAVEPOINT` on error, then `reportSideEffectFailure`.
  - Sefin calls only after commit (`after()` from `next/server`).
- One active note per payment record: partial unique index on `payment_record_id` where `status <> 'cancelled'`.
- Tenancy: `payment_records` has no `tenant_id`. Every payment-record lookup joins `installments` and filters `installments.tenant_id = :tenantId`. A taker update targets only the patient of the selected payment's financial entry.
- Competence default: BR day of `procedure_records.performed_at`, else `appointments.date`, else BR day of `payment_records.paid_at`; clamp to `brToday()` if later. Request option `competence: 'today'` sets `brToday()`.
- Roles: setup = owner. Emit/download/resend email = owner, receptionist, financial. Saving taker CPF/address from the emit dialog = owner, receptionist (same as patient update); a financial user gets the missing-data error. Cancel = owner, financial.
- Error codes (column `error_code`):
  - transient (cron retries, max 5 attempts): `provider_error`
  - needs a person (cron skips, manual "Tentar de novo" allowed, snapshot rebuilt): `invalid_request`, `missing_taker_data`, `not_configured`, `certificate_expired`, `unauthorized`, `reconcile_unavailable` (manual retry reconciles first, never emits blind)
  - final (never retried): `reconcile_ambiguous`, `payment_reversed`
- Batches: manual emit at most 20 payment record ids; cron `maxDuration = 300`, soft deadline 240 s, batch 20.
- Audit (`createAuditLog`, `entityType: 'nfse_document'`): `create` once when a document becomes `issued` (including reconcile adoption), `update` when cancelled. Setup changes: `entityType: 'nfse_settings'`, no secrets.
- All plans; no `checkPlanFeature`. pt-BR UI copy. No Claude attribution in commits. Comments only per the user's comment rule.
- Migration `web/src/db/migrations/0048_nfse.sql`: additive, `IF NOT EXISTS`, `--> statement-breakpoint`, RLS enabled, no policies.
- Tests: load `test-audit` first; each test names its regression. Integration tests guarded by `RUN_INTEGRATION = Boolean(process.env.DATABASE_URL_TEST || process.env.RUN_DB_TESTS)`; run `pnpm --filter @floraclin/web test:db:up`, then `RUN_DB_TESTS=1 pnpm --filter @floraclin/web exec vitest run <file>`.
- Agents do not commit. The orchestrator commits after each group (`feat(nfse): ...`).

## Review Focus

1. Double "Emitir", two concurrent emit requests, or cron plus manual: exactly one Sefin `emit` and one active row (Task 2 `insert race`, Task 5 `claims once`, Task 7 `concurrent POST`).
2. Sefin timeout after authorization, or reconcile itself unavailable: next attempt reconciles and adopts, never emits a second DPS; reconcile failure emits nothing (Task 5).
3. Reversal while a document is pending, processing, or issued: no note stays active for a reversed payment (unless the user unchecked cancel for an already-issued note) (Task 5 `reversal during emission`, Task 6).
4. Multi-record card reversal and process death during cancellation: every requested cancellation is retried by the cron until done (Task 5 `cron retries a requested cancellation`).
5. Email requested without patient email or Resend failure: note stays `issued`, no error to the payment flow (Task 5).
